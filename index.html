The clkMemIndex contract

clkMem is exactly 3× clk_sys off the same VCO, so a clk1x-domain toggle re-locks a mod-3 counter on every clk1x edge: index 0 is the coincident edge (NDS.sv:229–238). These are related clocks, so crossings are timed paths, not synchronisers.

Three separate modules depend on a specific phase, and none of them would work on a different one:

  • nds_mainram only launches an SDRAM op at index 0 — rtl/nds_mainram.vhd:178
  • the renderer VRAM feed only accepts a held request at index 2, the edge coincident with clk1x, so both ends agree which edge was the transfer — NDS.sv:922
  • done pulses are raised at index 1 so they are exactly one clk1x period wide — NDS.sv:870, NDS.sv:939

The ARM9 “island” — a domain that is currently 1 : 1

nds_top still has a clk2x port and a full clk1x↔island bridge (rtl/nds_top.vhd:837–1044: toggle-based requests, edge-detected dones, payload latches). But NDS.sv:1017 ties clk2x to clk_sys. The island exists in the RTL and runs at the system clock.

There is no ISLAND generic on nds_top. ISLAND is a testbench generic (sim/tb_top_frame.vhd:61); in hardware the ratio is whatever NDS.sv drives. The comment at rtl/nds_top.vhd:66 still claims clk2x is “PLL outclk_3, 50.270973 MHz” — the PLL declares three outputs (rtl/pll/pll_0002.v:27) and there is no outclk_3.

Dot cadence

A line is 355 dots × 6 = 2,130 clk1x cycles; a frame is 263 lines (192 visible + 71) = 560,190 (rtl/nds_gpu_timing.vhd:80, :7). The GPU is ce-paced 1-of-GPU_CE_DIV=3 (rtl/nds_top.vhd:54), so relative to the CPUs the frame is 3× long. gpu_full_pace on OSD status[10] switches it to 1-of-1 (NDS.sv:1038).

Scanout

256×384 active in a 533×526 frame, pixel ce = CLK_VIDEO/4 = 16.757 MHz → 59.77 Hz (NDS.sv:1205–1214). Both screens stack vertically, single-buffered, free-running.

DDR3 clock

DDRAM_CLK is assigned clk_sys (NDS.sv:542), so every DDR3 pager in NDS.sv is plain clk1x logic. Only SDRAM lives on clkMem.

03

Memory topology

who reaches which memory, through which channel, and where the sharing hurts

Two facts do the most work here. SDRAM ch2 is shared — main RAM owns it and the CPU's VRAM A–D path borrows it through a park-and-drain handshake. SDRAM ch1 is the renderer's, read-only, and holds exactly one request at a time. Everything else goes to DDR3 on its own channel.

Per-CPU reach into on-chip stores is a decode question, not a channel question — see the address maps in panel 04.

05

The renderer request chain

one BG pixel's tile fetch, drawer to SDRAM — where current work is

Each 2D engine holds ten drawer instances, but only four BG layers: BG0–BG3 each pick one drawer by mode, so BG2/BG3 have a text, an affine and an extended drawer wired in parallel with the unused ones muted (rtl/nds_gpu2d.vhd:999–1010). The BG arbiter multiplexes only those four onto one channel. OBJ, BG ext-palette and OBJ ext-palette are three further independent channels straight into nds_vram (rtl/nds_top.vhd:1719–1736) — eight renderer channels for two engines.

The live failure, and why simulation missed it for months

NDS.sv:917 makes vrsrv_ready a real back-pressure level: silicon permits exactly one A–D renderer read in flight. Until commit 5cf5fe0 the testbench's memory model accepted a request every cycle and never connected vrsrv_ready at all, so no bench had ever exercised the path — tb_gpu2d, tb_gpu2d_frame, tb_gpu2d_timed, the drawer equivalence bench and fbdiff all passed against a memory that cannot say no.

With VRSRV_ONE=1 the reported hardware white screen reproduced in minutes. The cause was a livelock, not slowness: an over-budget line was restarted from tile 0 by every following drawline, so it could never finish. The gate at rtl/nds_gpu2d.vhd:618 now drops a drawline that lands on a busy drawer, and the request handshake became held valid/ready at both ends.

Beware the metric that hid this. renders counts line_busy rising edges, so a renderer that never goes idle reports one render per frame regardless of what it finished — and 0 when line_busy is still high at the frame boundary. Quote done= and dropped= instead.

Status: fixed and measured under hardware-shaped back-pressure in simulation; not verified on silicon. All of it is nvc against a model of ch1, and the 64-bit path assumes sd_ch1_dout[63:0] is the aligned line in halfword order — read off sdram.sv, never observed on hardware. There is no renderer-side counter readable from the HPS yet, so a first hardware run can only say “something / nothing on screen”. Anything headed for silicon should be run with VRSRV_ONE=1.

Why the channel is 64 bits

sdram.sv reads four halfwords per access (BURST_LENGTH=4, rtl/sdram.sv:74) and a sequential burst wraps inside its aligned 8-byte block. Asking for the aligned line instead of a word makes the wrap irrelevant and doubles the yield per access (rtl/nds_vram.vhd:204–210).

Why the line cache is per channel

One 8-byte line each, indexed by channel — no associative search, no channel can evict another's. Measured on the mode-0 bench: 76% of A–D reads removed. A single shared line measured 1%, because eight channels interleaving destroy it (rtl/nds_vram.vhd:413–427).

GPU_FAST is off, and superseded

nds_gpu2d_fast is always instantiated (rtl/nds_top.vhd:1806) but GPU_FAST=0 (nds_port_wrap.vhd:176) elaborates the gslow branch, which wires straight through on clk1x. The gfast branch (rtl/nds_gpu2d_fast.vhd:241) runs both engines on clkMem; it bought 31% where the pipelined drawer bought 5.7×, and it still speaks the old done-based VRAM protocol, so it now stalls.

Where the cost was

Before the rework: 5,829 cycles per rendered line against 2,130, 95% of it inside any_bg_busy, 21.7 cycles per pixel in the text drawer (rtl/nds_gpu2d_fast.vhd:8–11, rtl/nds_drawer_text.vhd:29). The v2 drawer runs its fetch ahead of its pixels with a 4-deep tile queue and reports 1,134 cycles/line, 189/192 lines — in simulation, at that bench's latency.
